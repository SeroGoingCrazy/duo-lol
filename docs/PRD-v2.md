# PRD：英雄联盟匹配搭子（正式版 v2）

> 状态：草稿，待 Jacky 确认 · 2026-10-19
> 在原型 [PRD.md](./PRD.md) 之上扩展。预测模型、数据范围（美服、单双排 queue 420）和红线不变，冲突时以本文为准。
> 术语见 [CONTEXT.md](../CONTEXT.md)，关键决策见 ADR-0004 到 ADR-0007。

## 1. 目标

把原型做成一个能上线的网站：玩家注册并绑定自己的 Riot 账号，网站像 Tinder 一样一次给他看一张**卡片**，卡片按和他的**预测胜率**从高到低排；他右滑**喜欢**、左滑**跳过**，双方都喜欢就是**互选**，这时才互相看到 Riot ID 和联系方式。

原型的"查组合"保留，作为不登录也能用的入口。

## 2. 从 Tinder 借什么、不借什么

逆向拆了 Tinder 的核心机制，按"对上分有没有帮助"取舍：

| Tinder 机制 | 本产品 | 原因 |
|---|---|---|
| 一次一张卡、左滑右滑 | 采用，同时提供按钮和键盘（← →） | 决策成本低；按钮保证桌面端和无障碍可用 |
| 双向确认才能联系（double opt-in） | 采用，**互选**前不显示 Riot ID 和联系方式 | 防骚扰的关键，也是陌生人敢用的前提 |
| 被跳过的人不知道 | 采用 | 不制造负面反馈 |
| 撤销上一次跳过 | 采用，免费 | 误滑很常见，Tinder 拿它收费，我们不收 |
| 每日喜欢次数上限 | 采用，作为防刷手段 | 防止有人对所有人右滑，见 §8 |
| 按"受欢迎程度"排序（Tinder 早期的 Elo 魅力分） | **不采用**，只按预测胜率排 | 红线：每项排序依据都要能变成一条理由；受欢迎程度解释不了"能不能上分" |
| 超级喜欢、付费加速曝光 | 不采用 | 原型到上线阶段不做付费 |
| 站内聊天 | 首发不做 | 需要内容审核；互选后用游戏内加好友和 Discord |
| 地理位置 | 不采用 | 只服务美服，位置无意义 |

### 2.1 Tinder 网页版的滑卡实现（REA 逆向，2026-10-19）

用 REA 在本机无头浏览器打开 tinder.com，未登录，只读取它公开下发的 JS（webpack 运行时和 `async-recs-feature` 等分包），没有登录、没有调用它的接口，也没有复制代码。以下是**静态读到的**逻辑；登录后的运行时行为没有观察，结论属于推断。证据：REA Evidence `ev_6c705979…`（首页加载与分包清单），以及 `async-recs-feature-ea49ce46…js` 中的 recs reducer 和 loadRecs saga。

| 观察到的机制 | 我们怎么用 |
|---|---|
| **乐观滑卡**：滑动瞬间就把卡片从队列头部移走，并记下"上一张"；如果服务器回复"喜欢次数用完"或"操作被拦截"，再把卡片塞回队列头部 | 照做。滑卡不等接口返回，失败时卡片弹回，并提示原因 |
| **撤销只有一层**：只保存上一张卡片，撤销就是把它放回队列头部 | 照做，只能撤销最近一次跳过 |
| **喜欢的接口直接返回是否配对成功**：同一个响应里带回配对结果和剩余次数，不需要另外轮询 | 喜欢接口直接返回 `mutual_like` 和今日剩余喜欢次数，互选弹窗当场出现 |
| **预取**：队列少于 10 张时自动拉下一批 | 照做，剩余少于 10 张时拉下一页 |
| **客户端二次去重**：新拉来的卡片会再过滤掉已滑过、已拉黑的人 | 服务端过滤为主，客户端再去重一次，防止并发拉取时重复出现 |
| **牌堆耗尽时退避重试**：拉不到新卡时等待时间每次乘 1.5，有上限；服务器也可以指定等多久 | 照做。牌堆空时按退避间隔重试，因为新会员加入或预测刷新后会有新卡 |
| **配对或拉黑后从所有队列里移除对方** | 照做 |
| **多队列**（主推荐和各个"探索"分类，滑掉一张会从所有队列里删除） | 首发只有一个牌堆，不做分类 |
| 代码里有 "Duos" 推荐类型（Tinder 的两人组队模式） | 和我们的"组合"不是一回事，不借鉴 |

## 3. 用户流程

1. **注册与绑定**（ADR-0005）
   1. 用 Discord 登录。
   2. 输入自己的 Riot ID，网站随机指定一个召唤师头像，玩家在客户端换上后点"验证"，网站读到头像一致即绑定成功。一个 Riot 账号只能绑一个会员。
   3. 填偏好：想打的位置（最多 2 个）、是否同意被推荐（默认不同意，必须主动勾选）、互选后是否展示 Discord 名。
   4. 后台拉取他本赛季最近 100 场单双排（原型的进度条流程）。少于 20 场即**数据不足**，按原型 §2.3 让他自选英雄。
2. **滑卡**（ADR-0006）
   - 牌堆只含**推荐池**里的会员：同意被推荐、按 Riot 规则能和他双排、最近 14 天登录过、双方都没拉黑、他还没滑过。
   - 按预测胜率从高到低发牌。
   - 卡片内容：段位、建议位置分配（"你打中单，他打打野"）、预测胜率和胜率差、最佳英雄组合前 3、至少 3 条理由。**不显示** Riot ID。
   - 右滑喜欢，左滑跳过，可撤销上一次跳过。
   - 牌堆滑完显示"暂时没有更多"，并引导去"查组合"。
3. **互选**
   - 双方都喜欢时弹出"互选成功"，并进入"我的互选"列表。
   - 互选后双方看到对方的 Riot ID 和（若对方允许）Discord 名，页面提示"在客户端加好友"。
   - 可以取消互选；取消后对方列表里也消失，不通知对方。
4. **拉黑与举报**：任何卡片或互选都能拉黑（双方从此互不出现）和举报（附理由，进人工队列）。
5. **账号管理**：随时关闭"同意被推荐"（立刻退出推荐池），或注销账号（删除会员数据和滑卡记录，见 §9）。
6. **查组合**（原型功能，不登录可用）：输入两个 Riot ID 看预测胜率和理由。"找搭子"并入滑卡，不再单独存在。

## 4. 预测模型

沿用原型 PRD §3 和 ADR-0001，不改算法。正式版只改两件事：

- **结果缓存**：一对会员的预测结果连同理由、模型版本和计算时间一起存下来（ADR-0006），发牌时直接读，不现算。
- **版本号**：模型参数（先验场次、段位差表）每次变更都升模型版本，缓存按版本失效，避免同一对人在两张卡上看到不同数字。

## 5. 数据

- 全服统计在上线前完全切换为自有数据，停用 OP.GG（ADR-0003）。
- 抓取从"本地脚本 + SQLite"改为"云端作业队列 + Postgres"（ADR-0004、ADR-0007）。本地 SQLite 继续用于开发和离线训练。
- 会员的对局：注册时拉一次，之后每天增量刷新一次，有新对局才重算他的预测。
- 非会员玩家只用于全服统计，不出现在推荐池，也不在网站上展示个人信息。

## 6. 架构总览（ADR-0004）

```
浏览器
  │
  ▼
Next.js（web/，部署在 Vercel）
  · 页面、登录（Auth.js + Discord）、滑卡、互选、拉黑举报
  · 只写 app 库；预测相关一律调 Python API
  │  内部 HTTPS + 服务间密钥
  ▼
Python API（data/，部署在 Fly.io 或 Railway，美东）
  · 预测、查组合、玩家资料、头像验证
  · 只写 data 库
  │
  ├── 作业 worker（同一份代码，单进程）
  │     · 唯一持有 RIOT_API_KEY 并调用 Riot API 的进程
  │     · 统一限流、处理 429 和 Retry-After
  │     · 任务：拉会员对局、增量刷新、重算预测、算全服统计
  ▼
Postgres（Neon，美东）
  · schema app：会员、登录、偏好、滑卡、互选、拉黑、举报
  · schema data：玩家、对局、参与者、全服统计、预测缓存、作业队列
```

- **为什么分两个服务**：模型和抓取已经是 Python，重写成 TypeScript 会让两套算法分叉；网站和登录生态在 Next.js 最成熟。演示线程已经在做 Python API，正式版沿用这条边界。
- **作业队列放在 Postgres**（`SELECT … FOR UPDATE SKIP LOCKED`），不引入 Redis：规模不大，少一个要运维的东西。
- **只有 worker 调用 Riot API**：限流只在一个进程里做，最简单也最不容易超限。Python API 需要 Riot 数据时投递作业并返回进度。

### 6.1 滑卡接口（Next.js）

| 接口 | 作用 |
|---|---|
| `GET /api/deck?cursor=` | 返回下一页卡片（默认 20 张）；牌堆空时返回 `retry_after` 秒数 |
| `POST /api/swipes` `{to, action}` | 记录喜欢或跳过；返回 `mutual_like`（是否互选）、`likes_remaining`；次数用完返回 429 |
| `POST /api/swipes/undo` | 撤销最近一次跳过 |
| `GET /api/mutual-likes` | 我的互选列表，只有这里返回对方 Riot ID 和 Discord 名 |

## 7. 数据库（概要，字段在实现时用迁移定）

**app（Next.js 写，Drizzle 迁移）**

| 表 | 内容 |
|---|---|
| `members` | 会员；`puuid`（唯一）、`verified_at`、`last_active_at`、`deleted_at` |
| `auth_accounts`、`auth_sessions` | Auth.js 标准表（Discord 账号、会话） |
| `member_prefs` | 想打的位置、`recommend_opt_in`、`show_discord`、自选英雄 |
| `swipes` | `from_member`、`to_member`、`action`（like/pass）、`created_at`；每对唯一 |
| `mutual_likes` | 互选：两人、`created_at`、`cancelled_at` |
| `blocks`、`reports` | 拉黑、举报（理由、处理状态） |
| `verification_challenges` | 头像验证：指定头像、过期时间 |

**data（Python 写，SQL 迁移放 `data/migrations/`）**

| 表 | 内容 |
|---|---|
| `players`、`matches`、`participants` | 现有 SQLite 表原样迁移 |
| `champion_stats`、`champion_pair_stats` | 按版本、段位、位置预先汇总的全服统计，`OwnDataSource` 改为读这两张表 |
| `pair_predictions` | 两个 `puuid`、预测胜率、胜率差、位置、英雄组合和理由（JSON）、`model_version`、`computed_at` |
| `jobs` | 作业队列：类型、参数、状态、进度、重试次数、`not_before`（用于 Retry-After） |

规则：**每个 schema 只由一个服务写**；另一个服务需要就走 API。`app.members.puuid` 是两边唯一的连接点。

## 8. 防滥用

- 每个会员每天最多 100 次喜欢，跳过不限。这是防刷上限，不影响排序，可以调整。
- 被 3 名不同会员举报的账号自动暂停推荐，等人工处理。
- 绑定必须过头像验证，防止冒用别人的 Riot ID。
- 所有写接口按会员限频。

## 9. 合规与隐私（上线前必须完成）

- 申请 Riot Production Key；上线前核对 Riot 开发者政策对"组队/找搭子"类产品的要求。
- 拿到正式 Key 后申请 Riot Sign On（RSO），用它替换头像验证（ADR-0005）。
- 网站页脚加"非 Riot 官方产品"声明。
- 隐私政策：说明收集哪些数据、用途、保存多久。
- 注销账号后 30 天内删除会员数据、滑卡和互选记录；对局数据作为全服统计的一部分保留，但不再与该会员关联。
- `RIOT_API_KEY` 只存在于 Python 服务的环境变量里，不进 Next.js、日志和前端。

## 11. 验收标准

在原型 §5 三条之外：

1. **绑定**：新会员从登录到绑定完成不超过 3 步页面操作；头像不一致时给出明确提示。
2. **发牌**：已有预测缓存时，打开滑卡页 1 秒内出第一张卡；牌堆顺序与预测胜率一致。
3. **互选**：双方喜欢后，两人刷新页面都能在"我的互选"看到对方 Riot ID；互选前任何接口都拿不到对方 Riot ID。
4. **退出**：关闭"同意被推荐"后，此人不再出现在任何人的新牌堆里。

以上也是 Playwright 端到端测试的依据。

## 12. 待定（我先按默认做，可以改）

- **登录方式**：Discord 登录 + 头像验证，拿到 RSO 后换成 RSO（默认，ADR-0005）。
- **互选后展示什么**：Riot ID 必展示，Discord 名由本人决定（默认）。
- **牌堆是否混入"探索"卡**（预测胜率不是最高、但能帮模型学习的人）：首发不混，严格按胜率排（默认）。
- **被跳过的人多久后重新出现**：不再出现，除非对方的位置或段位变了（默认）。
- **托管平台**：Vercel + Fly.io/Railway + Neon（默认，均有免费或低价档位，可换）。
