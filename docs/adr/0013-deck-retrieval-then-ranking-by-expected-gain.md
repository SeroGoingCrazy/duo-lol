# 牌堆改为召回加排序；排序按"回滑概率 × 胜率差"，每一项都能变成理由

取代 ADR-0006 中"严格按预测胜率排序"和"发牌时只读预先算好的预测"两点；ADR-0006 拒绝按受欢迎程度排序的理由仍然成立。

现在的牌堆没有召回：每次把推荐池按最近活跃取前 4000 人，交给 Python 现算再排序。会员一多，预测胜率最高的人可能因为不够活跃进不了候选，现算也越来越慢。所以改成两段（Jacky，2026-10-22）：

- **召回**：几路并行取候选（段位和位置、英雄组合倒排表、喜欢我的人、现在想打、`pair_predictions` 中胜率最高的若干对），合并去重，过滤后进入预测缓存。每路取多少是存储和速度的取舍，不进入任何公式。召回和预测在 Python 侧（`data` 库）。
- **排序**：在 Next.js 侧（要用 `app` 库的滑卡数据），按**预期收获 = 回滑概率 × 胜率差**排，"你们现在都想打"的人单独排在最前一组，胜率差不大于 0 的人排在最后。

为什么加回滑概率：推荐一个胜率很高但几乎从不右滑的人，你右滑了也很难互选，北极星（互选后一起打）不会涨。Jacky 在三个方案里选了这个（A 只按预测胜率；B 预测胜率加可解释的项；C 用日志训练排序模型），C 要等曝光日志攒够数据再评估。

它和 Tinder 的"受欢迎程度"不同：回滑概率是**对方会不会右滑**（他自己的右滑率），不是**别人多喜欢他**，所以不会让热门的人越来越热门，并且能写成理由（"TA 已经喜欢你了""TA 右滑比较少，约 x%"）。回滑概率 = (他的喜欢次数 + k × 全站右滑率) / (他的滑卡次数 + k)，k 和全站右滑率用滑卡日志按 beta 分布拟合，不手填；日志不够时一律取全站右滑率，排序退化为按胜率差。预测模型（DraftGap 的 Elo 分数相加）本身不变，卡片上的搭配评分和预测胜率也不变，只有顺序变。

代价：牌堆顺序不再和预测胜率一致，需要在卡片上用理由解释为什么这张排在前面；同时要从现在开始记录曝光日志，才能评估这次改动和以后拟合。新会员曝光卡和热门会员降权以后再做。
