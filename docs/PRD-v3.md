# PRD：英雄联盟匹配搭子（v3：聊天、更像 Tinder、推荐升级）

> 状态：草稿，待 Jacky 确认 · 2026-10-22
> 在 [PRD-v2.md](./PRD-v2.md) 之上扩展。预测模型、数据范围（美服、单双排 queue 420）和红线不变，冲突时以本文为准。
> 术语见 [CONTEXT.md](../CONTEXT.md)，关键决策见 ADR-0011 到 ADR-0014。

## 1. 目标

PRD-v2 的滑卡、互选、喜欢我的人、拉黑举报已经上线，"滑"这一段已经很像 Tinder。差距在**互选之后**：互选了只能拿着 Riot ID 去游戏里加好友，网站上什么也做不了。v3 做三件事：

1. **站内聊天**：互选后的两人可以在网站上直接聊，约好位置和时间再进游戏。
2. **更像 Tinder 的体验**：互选和消息的主界面、实时通知、手机优先、卡片和按钮的样子。
3. **推荐升级**：牌堆从"取最近活跃的若干人现算再排序"改成**召回 + 排序**两段，排序在预测胜率之外加入**回滑概率**。

**北极星指标**：互选后 7 天内两人一起打过至少 1 局单双排的比例（从**一起打的战绩**算）。聊天和推荐的改动都看它有没有涨。

## 2. 离 Tinder 还差多少

对照 2026-10-22 main 上的网站，结论：

| 已经一样 | v3 补上 | 不借 |
|---|---|---|
| 一次一张卡，拖动带旋转和印章，键盘 ← → | 站内聊天（§3.2） | 按受欢迎程度排序、付费买曝光（红线，ADR-0013） |
| 双向确认才能联系 | "新互选"头像行 + 消息列表（§3.1） | 用户上传照片、GIF（要图片审核，对上分没帮助） |
| 撤销、喜欢我的人（都免费） | It's a Match 弹窗里直接发消息（§3.3） | 地理位置、Passport（只服务美服） |
| 卡片分页、互选弹窗 | 实时角标、浏览器推送（§3.5） | Tinder 的品牌配色和 logo |
| 每日喜欢上限、拉黑、举报、筛选 | 手机优先、图标按钮、英雄原画背景（§3.6） | 付费会员（ADR-0014） |
| | 认证标志、在线状态、资料话题（§3.6） | |
| | 超级喜欢（免费，§3.4） | |
| | 召回 + 排序（§5） | |

## 3. 用户流程（新增和改动的部分）

### 3.1 找搭子页的布局

照 Tinder 网页版：

- **电脑**：左栏从"互选 / 喜欢我的人"两个标签改成三块，从上到下：
  1. **新互选**：一排圆形头像，是还没发过消息的互选，最新的在左。点开进对话。
  2. **消息**：有消息的对话，按最后一条消息时间排序；显示对方头像、名字（互选后可见的 Riot ID）、最后一条消息的前几个字；未读加粗并带圆点。
  3. **喜欢我的人**：入口按钮带人数，点开是原来的列表。
  
  中间是牌堆；打开对话时，中间换成对话，右边换成对方的卡片（3 页照常翻），顶部有"返回牌堆"。
- **手机**：底部标签栏三项：**滑卡**、**消息**（互选和对话，带未读数）、**我的**（账号和偏好）。卡片占满屏幕，动作按钮在卡片下方。
- 不设互选过期（Tinder 不过期；推荐池小，过期会白白丢掉搭子）。很久没说话的对话自然沉到消息列表下面。

### 3.2 聊天（ADR-0011、ADR-0012）

- **谁能聊**：只有处于**互选**状态的两人。没有互选的人之间没有任何能发消息的入口，双向同意仍然是陌生人敢用的前提。
- **能发什么**：文字（每条最多 500 字）和表情；**快捷开场白**（"现在来一把？""我打 {位置}，你打 {位置}？""今晚 {常玩时间} 有空吗？"，从两人的卡片资料填进去）；**邀请卡**：一键发出"想现在双排"，对方点"好"后双方都看到 Riot ID 的复制按钮和"在客户端加好友"的提示。
- **不做**：图片、GIF、语音、视频、群聊、消息撤回和编辑。
- **已读**：对方读过后显示"已读"。会员可以在偏好里关掉，关掉后自己也看不到别人的已读（对等）。免费。
- **正在输入**：对方在输入时显示"正在输入…"，不存库。
- **取消互选**：对话从双方的列表里消失，不通知对方（沿用 PRD-v2）。消息按 §4 的保留期删除。
- **拉黑**：在对话里拉黑 = 取消互选 + 拉黑，双方从此互不出现。
- **限频**：每人每分钟最多 30 条，超了提示"发得太快了"。
- 联系方式（Discord、微信等）在聊天里**允许**发，因为双方已经互选；简介里仍然不允许（PRD-v2）。

### 3.3 互选弹窗

"互选成功"弹窗下方加一个输入框和三条快捷开场白，发出去就进对话；也可以点"继续滑"。

### 3.4 超级喜欢（ADR-0014）

- 每人每天 1 次，免费，卡片下方的星形按钮或向上滑。
- 对方在**喜欢我的人**里看到这张卡片排在最前，带"超级喜欢了你"标记；牌堆里刷到你时卡片上也有这个标记。
- **不改变你在对方牌堆里的位置**（ADR-0013 的排序本来就会把已经喜欢他的人排前面，见 §5.3）。

### 3.5 通知

| 事件 | 站内 | 浏览器推送 | Discord 私信 |
|---|---|---|---|
| 新互选 | 角标实时 +1，弹窗 | 是 | 是（已有） |
| 新消息 | 对话里实时出现，角标 +1 | 是 | 是，同一个对话在你离开网站期间只发一次 |
| 有人喜欢你 / 超级喜欢你 | 角标 | 否 | 否 |

- 推送和私信**不写对方是谁、不写消息内容**，只写"你有新的互选""你有新消息"。
- 浏览器推送要会员在"我的"里点开（浏览器会弹授权）。iPhone 上要先把网站"添加到主屏幕"才能收推送，页面上提示这一点。
- 不做邮件通知。

### 3.6 卡片与外观

- **动作按钮**：卡片下方一排图标按钮：撤销、跳过、超级喜欢、喜欢。这条取代之前"不用 Tinder 圆按钮"的规矩（Jacky，2026-10-22）；颜色沿用网站的 Arcane 主题，不用 Tinder 配色。
- **英雄原画**：卡片第 1 页的背景用对方招牌英雄（本赛季局数最多）的原画（Data Dragon splash，和英雄头像一样提前同步到 `web/public/`），上面压一层渐变保证字能看清。会员**不能上传照片**。
- **认证标志**：通过头像验证（以后是 RSO）的会员，卡片和对话顶部显示认证标志；没验证的不进推荐池（沿用 PRD-v2）。
- **在线状态**：卡片和对话显示"在线"（此刻开着网站）或"今天活跃"。会员可以在偏好里关掉，关掉后自己也看不到别人的（对等）。
- **资料话题**：选填，最多 3 条，从固定题目里选：我的招牌英雄、我在找一个……的搭子、我的雷点、上分目标。每条 100 字以内，和简介一样不能写联系方式。显示在卡片第 3 页理由的下面。
- **手机和 PWA**：网站可以"添加到主屏幕"，打开是全屏、没有浏览器地址栏；有启动图标和离线时的提示页。

## 4. 聊天的安全和审核（ADR-0012）

- **发送前检查**：消息命中辱骂词表或含有不在白名单里的链接时，不拦截，弹"确定要发吗？"。白名单：op.gg、u.gg、leagueofgraphs.com、discord.gg 等 LoL 常用站点，放在代码里的一张表。
- **接收方提示**：对方收到的消息如果命中辱骂词表，下方出现"这句话冒犯你了吗？"，点"是"直接进入举报（附上这条消息）。
- **举报**：对话里长按或右键一条消息"举报"，自动附上被举报的消息和它前后各 10 条作为快照，存进举报记录。举报后可以顺手拉黑。沿用 PRD-v2：被 3 名不同会员举报的账号自动暂停推荐。
- **管理员能看什么**：只能看举报里附带的快照，不能打开任何对话。管理员后台加"暂停聊天"操作（对方还在，只是不能发消息）。
- **保留期**：取消互选或任一方注销后，对话在 30 天后删除（留 30 天是为了处理期间收到的举报）；举报快照随举报一起保存到处理完成后 90 天。
- 隐私政策补上：聊天内容存在我们的数据库里，用于送达和处理举报，不用于训练、不给第三方（推送服务只经手"有新消息"这个事件，见 ADR-0011）。

## 5. 推荐系统：召回 + 排序（ADR-0013）

### 5.1 现在的问题

`web/lib/deckServer.ts` 的 `deck()` 每次打开都：取推荐池里所有符合条件的会员，按**最近活跃**排序截前 4000 人，整批交给 Python 逐个现算预测胜率，再按预测胜率排序。问题：

- 会员一多，预测胜率最高的人可能因为不够"最近活跃"根本进不了候选。
- 每次打开都现算几千对，越来越慢；PRD-v2 §4 计划的预测缓存（`pair_predictions`）还没做。
- 排序只看预测胜率，不管对方会不会回滑。推荐一个胜率很高但几乎从不右滑的人，你右滑了也很难互选。

### 5.2 召回

几路并行，每路各自取候选，合并去重后进入预测和排序。每路都只用硬条件和预先算好的表，不现算预测。

| 路 | 取谁 | 卡片上的理由 |
|---|---|---|
| ① 段位和位置 | 能双排（`can_duo`）且想打的位置和我互补的会员 | （没有单独理由，这是基础盘） |
| ② 英雄组合 | 我的常玩英雄和他的常玩英雄组成的**英雄组合**，在全服统计里组合加成排前列。用"英雄 + 位置 → 会员"倒排表查 | "你的 {英雄} 和 TA 的 {英雄} 组合胜率高" |
| ③ 喜欢我的人 | 喜欢了我、我还没滑过的人，全部进入 | "TA 已经喜欢你了" |
| ④ 现在想打 | 我开着"现在想打"时，同样开着的会员 | "你们现在都想打" |
| ⑤ 预测缓存 | `pair_predictions` 里和我预测胜率最高的若干对 | （由预测本身给理由） |

- 每路取多少人是**存储和速度的取舍**，写在配置里，不进入任何公式（和 ADR-0006 对 `pair_predictions` 上限的说法一样）。
- 牌堆筛选、拉黑、已滑过、已互选、暂停推荐，在召回后统一过滤（喜欢我的人不受筛选影响，沿用 PRD-v2）。
- **预测缓存**：召回结果中还没有缓存、或缓存的模型版本过期的对，由 worker 批量预测后写进 `pair_predictions`（PRD-v2 §4）。打开牌堆时先发已有缓存的卡片，其余的算好后在下一次预取时补上。
- 召回和批量预测在 Python 侧（`data` 库）；最后的排序在 Next.js 侧，因为它要用滑卡数据（`app` 库），沿用 ADR-0004 每个库只由一方写。

### 5.3 排序

排序按两人一起打能拿到的**预期收获**：

```
预期收获 = 回滑概率 × 胜率差
```

- **胜率差**：沿用模型的输出（预测胜率减去两人单排基线的平均值），DraftGap 的 Elo 分数相加不变。
- **回滑概率**：如果给对方看到我，他右滑的概率。
  - 他已经喜欢了我：1。
  - 否则用他自己的右滑率：`(他的喜欢次数 + k × 全站右滑率) / (他的滑卡次数 + k)`。k 是先验强度，和模型里英雄熟练度的先验场次同一个道理：滑得少的人向全站平均靠拢。k 和全站右滑率用滑卡日志按 beta 分布拟合（`data/` 里加一个脚本，和 `score_scale.py` 一样定期重算），不手填。
  - 日志不够拟合时，所有人的回滑概率都取全站右滑率，排序退化成按胜率差排。
- **两组**：
  1. 我开着"现在想打"时，**同样开着**的人排在最前一组，组内按预期收获排。理由："你们现在都想打"。
  2. 其余的人按预期收获排。
  3. 胜率差不大于 0 的人放在最后，按预测胜率排（这时乘回滑概率没有意义）。
- **每一项都能变成一条理由**：胜率差本来就有理由；回滑概率给出"TA 已经喜欢你了"或"TA 右滑比较少，约 {x}%"。理由放进卡片第 3 页，和预测的理由一起。
- 卡片上显示的**搭配评分和预测胜率不变**，只是顺序变了；所以牌堆顺序不再和预测胜率严格一致（PRD-v2 §11 第 2 条改写见 §10）。
- **以后再做**（Jacky，2026-10-22）：新会员曝光卡（每 10 张最多 1 张"新来的"）、对收到太多待处理喜欢的会员降权、用滑卡日志训练的排序模型。

### 5.4 曝光日志

为了评估排序、以后拟合回滑概率和训练排序模型，从现在开始记录**曝光**：每张发出去的卡片记一行（谁看到了谁、在牌堆第几张、当时的胜率差和回滑概率、模型版本、排序版本、时间）。滑卡已经有记录（`swipes`），两张表按 (看的人, 被看的人) 关联。

离线评估脚本按曝光算：右滑率、互选率、互选后 7 天内一起打过的比例（北极星），按排序版本对比。

### 5.5 C++ 打分引擎（可选实现）

召回后的批量预测（几百到几千对的 Elo 分数相加）和倒排表查询可以用 C++ 实现，pybind11 暴露成和 `predict.predict_pair` 一样的接口（Jacky 想做的 C++ 项目，2026-10-21）。要求：

- Python 实现保留为参考实现，测试逐对比较两边输出，误差为 0（同样的浮点运算顺序）或小于 1e-9。
- 没编译 C++ 扩展时自动用 Python 实现，`uv run pytest` 和 CI 不依赖编译器。
- 是性能优化，不改变任何结果和理由。

## 6. 架构（在 PRD-v2 §6 上的改动）

```
浏览器（PWA，Service Worker 收推送）
  │  HTTPS                         ▲ WebSocket（托管推送服务，只送"有新消息/新互选/正在输入"事件）
  ▼                                │
Next.js（Vercel）──── 发布事件 ───► 托管推送服务（Ably，ADR-0011）
  · 聊天接口：写 app.messages，再发布事件
  · 推送令牌：只能订阅自己的频道
  · 排序（§5.3）、曝光日志
  │
  ▼
Python API + worker（Fly.io）
  · 召回（§5.2）、批量预测、写 pair_predictions
  ▼
Postgres（Neon）
```

- **消息先落库再推送**：推送服务只是通知"有新东西"，客户端收到后从 Next.js 接口拉消息。推送服务挂了，客户端退回轮询（对话打开时 5 秒，否则 30 秒），不丢消息。
- 本地开发和端到端测试不设推送服务的 Key，就只用轮询，不需要外部服务。
- 浏览器推送用 Web Push（VAPID 密钥在 Vercel 环境变量里），Next.js 的服务端直接发，不经过推送服务。

### 6.1 新接口（Next.js）

| 接口 | 作用 |
|---|---|
| `GET /api/conversations` | 新互选 + 消息列表：对方、最后一条消息摘要、未读数 |
| `GET /api/conversations/:id/messages?before=` | 一页消息（默认 50 条），从新到旧 |
| `POST /api/conversations/:id/messages` `{body, kind}` | 发消息（`kind`：text / opener / invite）；返回存好的消息；限频返回 429 |
| `POST /api/conversations/:id/read` | 标记读到哪一条 |
| `POST /api/conversations/:id/typing` | 正在输入（只发布事件，不存库，按会员限频） |
| `POST /api/messages/:id/report` `{reason}` | 举报一条消息，自动带快照 |
| `GET /api/realtime/token` | 推送服务的令牌，只能订阅 `member:{自己的 id}` |
| `POST /api/push/subscribe`、`DELETE /api/push/subscribe` | 浏览器推送订阅 |
| `POST /api/swipes` `{to, action}` | `action` 多一个 `superlike`；返回多一个 `superlikes_remaining` |

`:id` 是对方会员的 id（一对互选只有一个对话）。

## 7. 数据库（在 PRD-v2 §7 上新增，字段在实现时用迁移定）

**app（Next.js 写）**

| 表 / 字段 | 内容 |
|---|---|
| `messages` | `id`、`member_a`、`member_b`（同 `mutual_likes`，a < b）、`sender`、`kind`、`body`、`created_at`、`flagged`（命中词表）；按 (a, b, created_at) 建索引 |
| `mutual_likes` 加字段 | `a_read_at`、`b_read_at`（各自读到的时间）、`last_message_at`（排序消息列表用）、`chat_paused_at` |
| `swipes.action` | 多一个值 `superlike` |
| `reports` 加字段 | `message_id`、`snapshot`（JSON，被举报消息和前后各 10 条） |
| `push_subscriptions` | 会员、endpoint、密钥、创建时间；推送失败 410 时删除 |
| `member_prefs` 加字段 | `read_receipts`、`show_online`、`notify_push`、`prompts`（JSON，最多 3 条） |
| `impressions` | 曝光日志（§5.4）：`viewer`、`shown`、`position`、`win_rate_delta`、`like_back`、`model_version`、`ranker_version`、`shown_at` |

**data（Python 写）**

| 表 | 内容 |
|---|---|
| `pair_predictions` | PRD-v2 §7 已规划，v3 正式建表 |
| `champion_players` | 倒排表：`champion`、`position`、`puuid`、局数、胜场；对局刷新时更新 |
| `like_back_prior` | 一行：全站右滑率、先验强度 k、拟合时间（像 `score_scale` 表一样） |

`like_back_prior` 要用滑卡数据，但滑卡在 `app` 库。拟合脚本通过 Next.js 的内部接口读汇总数（每个会员的喜欢次数和滑卡次数，不含对方是谁），不直接读 `app` 库。

## 10. 验收标准

在 PRD-v2 §11 之外：

1. **聊天只在互选后**：没有互选的两人，任何接口都发不出、读不到对方的消息；取消互选后双方都看不到这个对话。
2. **送达**：两个浏览器各登录一名互选会员，一方发消息，另一方在推送服务可用时 2 秒内、只有轮询时 10 秒内看到，刷新后仍在。
3. **推送服务挂掉不丢消息**：关掉推送服务后照样能收发（轮询）。
4. **举报快照**：举报一条消息后，管理员后台能看到这条消息和前后各 10 条，且看不到快照以外的消息。
5. **排序**：牌堆按 §5.3 的分组和预期收获排序；喜欢了我的人的回滑概率为 1；日志不够拟合时顺序等于按胜率差排序。（取代 PRD-v2 §11 第 2 条中"牌堆顺序与预测胜率一致"。）
6. **召回不漏**：推荐池里和我预测胜率最高的 20 人，不管多久没来过（14 天内），都会出现在我的牌堆里。
7. **手机**：390 宽的手机上，滑卡、看消息、发消息都不用横向滚动；能添加到主屏幕。

端到端测试用两个测试登录的会员（ADR-0009）互滑、互聊，推送服务不设 Key，走轮询。
